## 🌟 项目简介

**Limx Engine** 是一款面向影视级实时渲染的次世代图形引擎，基于 **C++23** 与 **Vulkan 1.4** 构建。区别于传统游戏引擎的"大而全"设计，Limx 采用**极简主义架构哲学**，专注于**视觉保真度**而非游戏逻辑，目标是成为"实时时代的数字暗房"。

### 为什么选择 Limx？

| 维度 | Limx 优势 |
|------|-----------|
| **🎨 画质** | 光谱渲染 + 硬件光追 + ReSTIR GI，影视级物理准确 |
| **⚡ 性能** | VisBuffer 架构，亿级面数直接渲染，无需拓扑优化 |
| **🤖 AI 原生** | Neural Radiance Cache、3D Gaussian Splatting 底层集成 |
| **📖 开源** | 核心引擎 Apache 2.0，打破技术黑盒 |
| **🪶 轻量** | <50 万行代码（UE ~4000 万行），专注渲染 |

| **Vulkan SDK** | 1.3+（引擎按本机 SDK 协商版本，1.4 可用则启用 1.4） | 1.4.350 |
| **Rust 工具链** | stable（用于构建 lbt/lht/lsc） | 最新 stable |
| **内存** | 16 GB | 32 GB+ |

### 关于第三方 SDK

`Source/ThirdParty/` **不纳入版本控制**（厂商 SDK 体积约 630 MB）。

**这不影响构建。** NvidiaDLSS 与 IntelOIDN 在构建系统中是 `External` 类型
模块，当前没有任何引擎模块依赖它们；目录缺失时 `lbt` 只会少发现两个模块，
构建、全部单元测试与场景渲染均不受影响（已实测）。

将来接入 DLSS 超分或 OIDN 降噪时，再按下列路径放置对应 SDK：

```
Source/ThirdParty/NvidiaDLSS/    # include/ + lib/
Source/ThirdParty/IntelOIDN/     # include/ + lib/
```

### 构建步骤

本项目**不使用 CMake**。构建由自研的 Rust 工具链驱动：`lbt`（构建）、
`lht`（反射代码生成）、`lsc`（着色器编译）。

```bash
# 克隆仓库
git clone https://github.com/LimxTeam/LimxEngine.git
cd LimxEngine

# 构建 Rust 工具链并发布到 Binaries/Tools
cd Programs && cargo build --workspace --release && cd ..
cp Programs/target/release/lbt.exe Binaries/Tools/
cp Programs/target/release/lht.exe Binaries/Tools/
cp Programs/target/release/lsc.exe Binaries/Tools/

# 编译着色器 + C++（lbt 内部会依次调用 lht 与 lsc）
./Binaries/Tools/lbt.exe build -s Source -c development

# 运行
./Binaries/Development/Win64/LimxLaunch.exe
```

### 验证与基准

```bash
# 全量验证：工具链 → 着色器 → 源码规则 → 构建 → 四套单元测试 → 显存回收自检
powershell Scripts/verify.ps1

# 渲染吞吐基准：同一场景下对照剔除与合批的收益
powershell Scripts/benchmark.ps1
```

### 运行参数

```bash
# 加载任意 OBJ / glTF / GLB 场景
LimxLaunch.exe --scene Content/Sponza/Sponza.gltf --camera-inside

# 压力场景 + 基准报告（N×N 个物体，渲染 300 帧后退出）
LimxLaunch.exe --grid 60 --frames 300

# 对照开关
LimxLaunch.exe --grid 60 --frames 300 --no-cull --no-sort

# 完整吞吐基准（五种配置对照，含 IBL 逐帧成本）
powershell Scripts/benchmark.ps1

# HDR 环境贴图 + 天空盒，固定机位截屏
LimxLaunch.exe --hdri Content/HDRI/sky.hdr --camera-pitch -0.35                --frames 30 --screenshot shot.ppm
```

| 参数 | 说明 |
|------|------|
| `--scene <路径>` | 导入 `.obj` / `.gltf` / `.glb` 场景 |
| `--scene-scale <倍数>` | 导入时的统一缩放 |
| `--camera-inside` | 相机置于场景内部（建筑内景用） |
| `--no-textures` | 不加载纹理，只保留材质常量 |
| `--grid <N>` | 构建 N×N 压力场景 |
| `--frames <N>` | 渲染 N 帧后输出基准报告并退出 |
| `--warmup <N>` | 计入统计前跳过的预热帧数（默认 60） |
| `--no-cull` / `--no-sort` | 关闭视锥剔除 / 状态排序 |
| `--reload-test` | 关卡切换自检：加载 → 卸载 → 再加载，报告显存回落 |
| `--hdri <路径>` | 加载 Radiance `.hdr` 作为环境贴图与天空盒 |
| `--sky-intensity <倍数>` | 天空强度的线性倍数（默认 1.0） |
| `--ibl-intensity <倍数>` | 环境光照强度的线性倍数（默认 1.0） |
| `--probe-irradiance` | 输出辐照度贴图六个面的中心值（数值校验用） |
| `--probe-brdf` | 输出 BRDF 查找表的采样网格（数值校验用） |
| `--material-grid <N>` | 构建 N×N 球体阵列（横向粗糙度，纵向金属度） |
| `--furnace` | 白炉测试：合成均匀环境 + 关闭直接光 |
| `--furnace-check` | 白炉自检：断言 IBL 各级预计算，以退出码报告 |
| `--camera-yaw <弧度>` / `--camera-pitch <弧度>` | 固定相机朝向，用于可复现的截屏对照 |
| `--screenshot <路径>` | 末帧截屏写入二进制 PPM（P6） |

## 第一章：设计哲学

### 1.1 核心设计原则

#### 原则一：极简主义 (Minimalism)

> **"每一行代码都必须证明其存在的必要性"**

| 维度 | 传统引擎 | Limx 方案 |
|------|----------|-----------|
| **代码规模** | UE ~4000 万行 | < 50 万行 |
| **依赖项** | 数百个第三方库 | 零 STL、最小外部依赖 |
| **功能范围** | 游戏逻辑 + 渲染 + 物理 + 音频 + 网络 | 纯渲染核心 |
| **编译时间** | 数小时 | 分钟级 |

**实现策略**：
- 拒绝"以防万一"的代码
- 每个模块必须有明确的单一职责
- 功能通过组合而非继承实现

#### 原则二：零开销抽象 (Zero-Overhead Abstraction)

> **"抽象不应引入任何运行时成本"**

| 抽象层 | 设计目标 | 实现手段 |
|--------|----------|----------|
| **类型系统** | 编译时类型安全 | C++23 Concepts + constexpr |
| **资源管理** | 零运行时开销 | RAII + 编译时生命周期验证 |
| **多态** | 静态分发优先 | CRTP + Policy-Based Design |
| **容器** | 缓存友好 | 自研 SOA 容器、内存池 |

#### 原则三：数据导向设计 (Data-Oriented Design)

> **"数据布局决定性能上限"**

```
传统 OOP 布局（AOS - Array of Structures）:
┌─────────────────────────────────────────────────────────┐
│ Object1: [Position][Normal][UV][Material][Transform]   │
│ Object2: [Position][Normal][UV][Material][Transform]   │
│ Object3: [Position][Normal][UV][Material][Transform]   │
└─────────────────────────────────────────────────────────┘
问题：遍历 Position 时，缓存污染严重

Limx DOD 布局（SOA - Structure of Arrays）:
┌─────────────────────────────────────────────────────────┐
│ Positions:  [P1][P2][P3][P4][P5][P6][P7][P8]...        │
│ Normals:    [N1][N2][N3][N4][N5][N6][N7][N8]...        │
│ UVs:        [U1][U2][U3][U4][U5][U6][U7][U8]...        │
│ Materials:  [M1][M2][M3][M4][M5][M6][M7][M8]...        │
└─────────────────────────────────────────────────────────┘
优势：连续内存访问，缓存命中率 > 95%
```

#### 原则四：显式优于隐式 (Explicit over Implicit)

> **"所有行为必须可预测、可追踪"**

| 禁止的隐式行为 | Limx 显式替代 |
|----------------|---------------|
| 隐式类型转换 | `explicit` 构造函数 + 显式转换函数 |
| 隐式内存分配 | 所有分配通过 Allocator 接口 |
| 隐式资源获取 | 显式 `Acquire()` / `Release()` |
| 隐式状态变更 | 不可变数据结构 + 显式状态机 |

#### 原则五：编译时计算最大化 (Compile-Time Maximization)

> **"能在编译时完成的，绝不留到运行时"**

| 计算类型 | 编译时实现 |
|----------|------------|
| **类型检查** | Concepts 约束 |
| **常量计算** | constexpr / consteval |
| **代码生成** | 模板元编程 |
| **配置验证** | static_assert |
| **字符串处理** | 编译时字符串哈希 |

#### 原则六：编译期反射 (Compile-Time Reflection)

> **"元数据由编译器生成，而非运行时查找"**

利用 C++23 的静态反射能力（或基于宏/模板的元编程），实现序列化、UI 生成和材质参数绑定的零运行时开销。

| 应用场景 | 编译期实现 |
|----------|------------|
| **属性序列化** | 编译时生成序列化代码，无需 RTTI |
| **UI 面板生成** | 材质编辑器属性面板由编译器直接生成 |
| **Shader 绑定** | 参数布局在编译时确定，零字典查找 |
| **反射查询** | 类型信息编译时内联，无运行时开销 |

### 3.2 子模块设计

#### 3.2.1 Vulkan RHI (Rendering Hardware Interface)

**职责**：封装 Vulkan API，提供类型安全的 GPU 资源管理接口。

| 组件 | 职责 | 创新点 |
|------|------|--------|
| **DeviceContext** | 管理 Vulkan 实例、物理/逻辑设备 | 自动选择最优 GPU，支持多 GPU |
| **CommandContext** | 命令缓冲区录制与提交 | 无锁命令池，线程本地分配 |
| **ResourceManager** | Buffer/Image/Sampler 生命周期 | 延迟销毁 + 帧级资源回收 |
| **PipelineCache** | PSO 缓存与热加载 | 磁盘持久化 + 异步编译 + Pipeline Library |
| **SyncManager** | Fence/Semaphore/Barrier 管理 | Timeline Semaphore 优先 |
| **BindlessManager** | 全局描述符管理 | Descriptor Indexing + 无限资源引用 |

**Vulkan 1.4 核心特性依赖**：

| 特性 | 用途 | 架构收益 |
|------|------|----------|
| **Dynamic Rendering** | 彻底移除 RenderPass/Framebuffer 对象 | 管线管理极简化，符合极简主义哲学 |
| **Descriptor Indexing** | 全局 Bindless 资源访问 | 材质系统支持无限纹理引用 |
| **Timeline Semaphore** | 精细化 GPU 同步 | 多队列并行，减少等待 |
| **Buffer Device Address** | GPU 指针直接访问 | 零绑定开销，支持 GPU-Driven |
| **Maintenance5** | 动态状态扩展 | 减少 PSO 变体数量 |

#### 5.2.1 核心概念

#### 6.2.2 高分辨率优化策略

针对 4K 等高分辨率场景，NRC 采用以下优化策略确保推理开销可控：

| 策略 | 实现 | 性能收益 |
|------|------|----------|
| **Half-Resolution Inference** | 半分辨率推理 + 双边上采样 | 推理开销降低 75% |
| **Checkerboard Training** | 棋盘格采样训练，隔帧交替 | 训练开销降低 50% |
| **Adaptive Query** | 仅对间接光照显著区域查询 NRC | 减少 30-50% 查询量 |
| **Temporal Accumulation** | 时域积累，复用历史推理结果 | 有效 spp 提升 4-8x |
| **Tile-Based Batching** | 按 Tile 批量推理，提升 GPU 占用率 | 吞吐量提升 20% |
